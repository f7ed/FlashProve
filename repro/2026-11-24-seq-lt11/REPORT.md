# FlashProve 序列长度实验：T = 2,048（lt 11），Vast.ai 单卡 H100（2026-11-24）

状态：**完成**。T = 2,048 端到端跑通（`YES`，退出码 0），全部测量做完，T = 1,024 的同机对照也做完。实例已销毁。

## 结论（到目前为止）

这次实验想回答一个问题：FlashProve 的程序能不能处理 2,048 个 token 的上下文？token 是模型处理文字的基本单位。一个 token 大约是一个词或半个词。仓库自带的完整规模配置 `target_full_f2` 用 1,024 个 token（参数文件里的行 `lt 10`，T = 2^10）。

| 问题 | 答案 |
|---|---|
| 只把 `lt 10` 改成 `lt 11`，程序能跑吗？ | **不能。** 验证器的规划调用（planning call）拒绝这个参数文件：`NO: forest-keys`。`cp_commit` 开始前会做同一个规划调用，所以 GPU 上什么都不会开始。 |
| 原因是什么？ | 输出头（output head）的查表证明里，键（key）的总数到了 $2^{32}$。程序要求少于 $2^{32}$。详细解释见下面「限制 1」。 |
| 改参数能绕过去吗？ | 只改参数不行。键的总数由词表大小 V 和 T 决定。保持 V = 202,048（Llama 4 Maverick 的词表）时，T = 2,048 一定超过。 |
| 改代码能绕过去吗？ | 有两条路。路线 A：放宽代码里的上限到 $2^{32}$，保持 V = 202,048。路线 B：不改这个上限，把 V 减到 131,072，再改 6 行参数。两条路都还要改 `rotary-table` 这个条件（见「限制 4」）。 |
| 做了什么？ | 两处代码改动（`78092cbc`：`rotary-table` 放宽到 lt 11；`d1cc7d98`：查表森林允许 $2^{32}$ 个键）。在一台按需的 H100 NVL 上，T = 2,048 的承诺、证明、验证全部通过，并做了单请求、多 batch、补 0 长度三组测量；再在同一台机器上对 T = 1,024 做了同样的事。总表见「总表：长度 × 批大小」。 |

**重要：** 这个分支上的 `cp_verify` 是改过的程序。它在 lt 11 下给出的 `YES`，是改过的 C++ 验证器的 `YES`。Lean 里证明过的验证器没有改，`guide/what-is-proved.md` 里的结论不覆盖它。

## 准备 lt 11 的参数文件

参数文件 `policy.txt` 的行 `lt` 决定上下文长度 T = 2^lt。它还有 32 行表的摘要（digest），`tsilu0` 到 `texp7`。其中 8 行 `trope0..7` 是 rotary 表的摘要。rotary 表存每个位置的旋转角的余弦和正弦。模型用它表示 token 的位置。T 变了，rotary 表就变了，摘要也要重算。

```
sed 's/^lt 10$/lt 11/' prover/examples/target_full_f2/policy.txt > base
python3 -I scales/policy_tables.py base > policy.txt
python3 -I scales/policy_tables.py --check policy.txt   # the 32 digest lines match the tables
```

`KL.bin`（每层的量化比例）直接复制 `target_full_f2` 的。它只有各层的记录，和 T、V 无关。

## 发现的限制

下面按遇到的顺序列出 lt 11 下的每一处限制。前三处由验证器的规划调用报出。规划调用是 `cp_verify -plan ...`。它只读公开的配置文件，不检查证明，在 CPU 上几秒钟跑完。

### 限制 1：`forest-keys`（键的总数到了 $2^{32}$）

三个规划调用对只改了 `lt` 和 `trope*` 的文件都返回 `NO: forest-keys`，退出码 1：

```
cp_verify -plan accounting <folder> 128
cp_verify -plan request policy.txt KL.bin 128 -prompt <2,050 words> -reply <1 word>
cp_verify -plan arrays <folder> 128
```

**这是什么。** 证明里有很多「查表」（lookup）的步骤。一个查表步骤声明：一组值（键，key）每一个都是一张公开表里的某一行。FlashProve 把一个子证明里的所有查表合成一个「森林」（forest）来证明。森林里每张表的每一行有一个计数（multiplicity），记录有多少个键落在这一行。这个计数用 32 个 bit 存。所以一个森林的键总数必须少于 $2^{32}$。代码位置：`verifier/src/vf_lookup_argument.h:130`（`forestShape`，`h.v() >= 32` 时拒绝）和 `prover/hiding/forest_plan.h:102`。底层引擎 `blocks/iop/lkp.h:306-308` 写了同样的条件。

**为什么 lt 11 会超。** 我们从 T = 1,024 的规划输出反推了每个森林的键数（取 log2，记为 v）。方法：`-plan request -fields` 列出证明的每个字段，一个森林的 sumcheck 轮数是 $v(v-1)/2$。

| 子证明 | v（T = 1,024） | v（T = 2,048） |
|---|---|---|
| 注意力（attention）A | 29 | 31 |
| 层（layers）G | 30 | 31 |
| 输出头 H | 31 | **32** |

输出头的森林在 T = 1,024 时已经是 $2^{31}$。它每个查表调用的键数是 $2^{l_J + \mathrm{lt}}$（`verifier/src/cp_verify.cpp`，`c.n = cd.lJ + lt`）。$l_J$ 由词表大小 V 决定：输出头要检查每个 token 的全部 V 个 logit。logit 是模型给每个候选 token 打的分。所以 T 翻倍，键数翻倍，到 $2^{32}$。

参数行 `lidb`（树的深度上限）帮不上忙：深度已经被最小的调用限制了。把 `callH` 行拆开也不减少键的总数。

### 限制 2：`hid-k-range`（矩阵超过 8,191 列）

把 V 减半以后，规划调用报 `NO: hid-k-range`。原因：几个承诺的矩阵的列数超过上限 8,191（`verifier/src/vf_smallness_packing.h`，`KCAP`）。每个矩阵有 $2^{\mathrm{lm}}$ 行，列数等于单元数除以行数。单元数随 T 增长，行数不变，列数就超了。

从 T = 1,024 的 `-plan arrays` 输出看最宽的矩阵：

| 矩阵 | T = 1,024 的列数 | 随 T 的增长 | 对应的参数行 | 改法 |
|---|---|---|---|---|
| `as`（注意力的分数）| 7,200 | 4 倍（单元数含 $2^{2\,\mathrm{lt}}$）| `lmS 16` | 改成 `lmS 18` |
| `af`（前馈层的激活，3 份）| 5,990 | 2 倍 | `lmaf 16` | 改成 `lmaf 17` |
| `hf`（输出头的 logit 边距等，4 份）| 4,816 | 2 倍 | `lmhf 16` | 改成 `lmhf 17` |

### 限制 3：`policy-iotaA` 和 `shape-call-H-*`（派生值要重写）

行 `iotaA_0` 必须等于 32 加注意力森林的树深度 dT。lt 11 时 dT 从 25 变成 26，所以 `iotaA_0 57` 要改成 `58`。行 `iotaH_0..5` 必须等于输出头每个调用的键位数减 dT。V = 131,072 时 `iotaH_0` 和 `iotaH_2` 从 1 变成 2。这些行「没有自由度」：程序自己算出一个值，文件里必须写同一个值。

### 限制 4：`rotary-table`（served condition，lt ≤ 10）

验证器只在「标准参数形式」下给 `YES`。它是一组按名字检查的条件（`verifier/docs/parameter-file.md`）。其中 `rotary-table` 要求 `lt` 最多 10。原因：仓库的测试 `scales/tests/table_ties.py` 只检查到 1,024 个位置。这个测试看 rotary 表的每一项离「舍入边界」（k + 1/2）有多远。离得太近，不同平台的数学库就可能算出不同的表。

`cp_commit` 开始前会运行旁边的 `cp_verify -plan request`。规划调用说文件不是标准形式时，`cp_commit` 拒绝这个文件（`cp-commit-not-standard`）。所以不改这个条件，GPU 上什么都跑不起来。

### 其他在 lt 11 下不构成限制的条件

| 条件 | 要求 | lt 11 时的值 |
|---|---|---|
| softmax 表（prover，`parameter_file.h`）| lt + S + 1 ≤ 24，S = 12 | 24，刚好满足 |
| prover 的注意力（`prover/attn/fork.cuh`）| lt ≤ 14 | 11 |
| `la`（`la 16`）| la ≥ lt + 1 | 16 ≥ 12 |
| `lB`（`lB 6`）| lB ≤ lt − 2 | 6 ≤ 9 |
| `lmS` | lmS ≤ log2 G + lt + lB = 20 | 18 |

## 代码改动（提交 `78092cbc`）

只改了 `rotary-table` 条件。改动有三个文件：

1. `verifier/src/vf_common.h`，函数 `rotaryServed()`：theta0 = 500,000 时允许 lt ≤ 11；theta0 = 10,000 时仍然只到 lt ≤ 10；dh ≤ 128 不变。theta0 是 rotary 表的底数。`target_full_f2` 用 500,000。
2. `scales/tests/table_ties.py`：theta0 = 500,000 时检查 2,048 个位置（原来 1,024）。theta0 = 10,000 时仍然检查 1,024 个位置。下限（floor）不变。
3. `verifier/docs/parameter-file.md`：`rotary-table` 那一行和「lt 最多 10」那一句。

**测试结果。** 完整的 `table_ties.py` 在 Mac 上运行，输出 `OK: 26 checks`，退出码 0。theta0 = 500,000、2,048 个位置：262,144 项，离舍入边界最近 9.321e-08（下限 9.3e-08），数学库至少要偏 2,559 个单位才会改变一项（下限 2,500）。这两个最小值出现在位置 387，也就是在 1,024 以内，和原来的测试一样。另外单独看位置 1,024–2,047：theta0 = 500,000 最小距离 3.64e-06，最小余量 7,300 个单位，满足下限；theta0 = 10,000 最小距离 9.01e-06，余量 73,600 个单位，**低于**它的下限 100,000。所以 theta0 = 10,000 不放宽。日志：[logs/ties/](logs/ties/)。

没有改 `forest-keys` 的上限（路线 A 的改动在另一个会话，见下面）。

## 路线 A（另一个会话在做）

另一个会话在同一台实例上做路线 A：保持 V = 202,048，把 `forest-keys` 的上限从「少于 $2^{32}$」放宽到「最多 $2^{32}$」。提交 `d1cc7d98`（在 `78092cbc` 之上）改了三处：`verifier/src/vf_lookup_argument.h`（`h.v() >= 33` 才拒绝）、`prover/hiding/forest_plan.h`（`p.v() > 32`）和 `blocks/numbers/blocks.h` 的 `plan_lookup`（accounting 里同一条规则的副本）。它的理由：另一条件「所有计数的和不能在域里回绕」（`no-wrap-pin-forest`）没有改；正好 $2^{32}$ 个键时，只有全部键落在同一个表行，32 位计数才不够，诚实的子证明不会这样。

要注意两点：

- 底层引擎 `blocks/iop/lkp.h` 的 `lkp_fault()` 写明条件是 $2^{v} < 2^{\text{planes}}$（planes = 32）。`cp_prove` 和 `cp_verify` 运行时不调用 `lkp_fault()`（只有测试调用），所以程序能跑。但这偏离了引擎写明的条件，这个改动只用于实验，不用于服务。
- 一个森林有 $2^{32}$ 个键时，键的编号刚好用满 32 位。代码里如果有 32 位的编号或移位，可能溢出。这要靠运行来发现。

路线 A 的参数文件在 [kit-lt11-V202048/](kit-lt11-V202048/)。和 `target_full_f2/policy.txt` 相比改了：`lt 11`、`lmaf 17`、`lmS 18`、`lmhf 17`、`iotaA_0 58`、`nminH 28`（原 27：这样输出头每个调用的键位数至少 28，`iotaH` 行不用改）和 8 行 `trope`。用改过的 `cp_verify`（`d1cc7d98`）做规划调用：两个都通过，退出码 4，标准形式（不再打印 `not the standard parameter form`）。proof 最多 24,963,908 字节，平均 24,484,802；key 和 entry 不变；输出头子证明 244 行（路线 B 是 175 行，T = 1,024 是 127 行）。日志：[logs/plan/](logs/plan/)（文件名带 `changed-verifier-d1cc7d98` 的两个）。构建记录：[logs/build/](logs/build/)，`cp_prove.build` 里 `commit: d1cc7d98...`。

承诺的工作量由权重决定，不由 T 决定，所以两列的差别主要是 GPU 的差别（NVL 没有降频：温度峰值 80 °C，忙时 SM 时钟平均约 1,438 MHz；PCIe 当时 87 °C、约 1,100 MHz）。在同一台 PCIe 卡上，T = 2,048 的 check 用了 639.9–640.1 s，和 T = 1,024 的 634.6 s 一样（被抢占的尝试里测到的）。

### 单请求，不同的覆盖长度（T = 2,048）

exact-match 策略下，被覆盖的每个 token 必须是模型在它前面所有 token 之后的首选，否则 `cp_prove` 不写 proof，只写一个空的 `.failed` 文件。我们没有工具在 T = 2,048 下生成新的首选序列。所以请求用 T = 1,024 的 `own_choices.req`（24 个 token 的提示词 + 1,000 个首选 token）后面补 1,024 个 token 0 做成，只改 e（覆盖到哪个位置）。假设是：位置 < 1,024 的首选不随 T 变。

每个请求单独一次 `cp_prove -in -out`（一个 batch，1 个请求），然后一次 `cp_verify`。时间是进程从启动到退出的墙钟时间（`measure.sh`，每秒读一次 `/proc/<pid>/status` 的 `VmHWM` 作为峰值 RSS）。

| 请求 | 覆盖的 token 数 | `cp_prove` 墙钟 | `cp_prove` 峰值 RSS | 结果 | proof 字节 | `cp_verify` 墙钟 | `cp_verify` 峰值 RSS |
|---|---|---|---|---|---|---|---|
| own_r23_e124 | 100（位置 24–123） | 100.4 s | 254,157,756 kB | `YES` | 24,478,108 | 30.1 s | 41,340 kB |
| own_r23_e224 | 200 | 99.4 s | 254,156,272 kB | `YES` | 24,491,100 | 30.1 s | 40,952 kB |
| own_r23_e524 | 500 | 100.4 s | 254,158,912 kB | `YES` | 24,479,268 | 30.1 s | 41,304 kB |
| own_r23_e1024 | 1,000 | 98.4 s | 254,155,080 kB | `.failed`，没有 proof | — | — | — |
| synthetic_next | 0（只问 y） | 100.4 s | 254,161,340 kB | `YES`，y = 98477 | 24,476,356 | 30.1 s | 41,116 kB |

结论：

- 覆盖 100、200、500 个 token 的时间和只问下一个 token 的时间一样（约 100 秒，差别小于 1 秒）。proof 大小的差别小于 0.1%。这和文档的说法一致：主要开销是对整个窗口做 prefill 和证明，覆盖多少 token 几乎不影响。
- 覆盖 1,000 个时失败。所以 T = 1,024 的首选序列在位置 524 到 1,023 之间的某一处，在 T = 2,048 下不再是首选。前 524 个位置一致。原因我们没有查：可能是注意力或归一化的某个整数运算和 T 有关。这是一个待查的问题，不影响其他测量。
- `cp_prove` 的 100 秒里，proof 在约 66 秒时写出（示例运行的文件时间戳），其余约 34 秒是进程退出时释放锁定内存。`cp_prove` 的峰值 RSS 约 254 GB，和 `cp_commit` 锁定的 236.9 GB 权重加工作内存相符。
- `cp_verify` 的峰值 RSS 只有约 41 MB。

### 多个 batch：`driver/measure_rate.py`（T = 2,048）

`measure_rate.py` 是仓库自带的测速脚本。它把 N × B 个请求（每个 T 个 token，只问下一个 token）一次放进 spool 目录，启动一次 `cp_prove` 服务（`-batch B -most-batches N`，`-memory lean,tensor-rooms=8`），从外面记每个 proof 文件出现的时间，最后对每个 proof 单独调用一次 `cp_verify`（`-j 4`，几个并行）。稳定速率 = B × T 个 token 除以相邻两批出来的平均间隔。每次 N = 3。

| B（每批请求数） | 稳定速率（token/s） | 每请求秒数 | 一批的用时（s） | 启动（s） | GPU 显存最大样本（MiB） | proof 大小（MB） | 结果 |
|---|---|---|---|---|---|---|---|
| 1 | 80.93 | 25.3 | 24.9–25.7 | 34.2 | 72,355 | 24.45–24.49 | 3/3 接受 |
| 8 | 155.54 | 13.2 | 105.1–106.1 | 33.8 | 92,093 | 24.47–24.50 | 24/24 接受 |
| 24 | 169.86 | 12.1 | 290.2–292.3 | 33.6 | 95,261 | 24.46–24.50 | 72/72 接受 |

观察：

- B 从 1 到 8，每请求时间从 25.3 秒降到 13.2 秒（一批 8 个只比一批 1 个慢 4 倍）。B 从 8 到 24 只再降 9%，而一个请求的等待时间从 106 秒涨到 291 秒。
- B = 24 的显存最大样本是 95,261 MiB，离这张卡的 95,830 MiB 只差约 570 MiB。更大的 batch 在这张卡上放不下。在 80 GB 的卡上，T = 2,048 时 B = 8（92 GB）就已经放不下。
- 文档（`guide/performance.md`，T = 1,024，真权重，H100 80 GB）：B = 1 时 17.41 token/s（58.8 秒一个请求），B = 24 时 111.23 token/s（9.2 秒）。这里 T 翻倍以后，B = 24 时每请求 12.1 秒，B = 1 时 25.3 秒。机器不同（NVL，没有降频）、权重不同（合成）、内存布局不同（`lean`），不能直接比。

怎么读这张表：

- **承诺**只和权重有关，和 T 无关。
- **单请求的证明**时间几乎不随 T 变：单请求时 GPU 大部分时间在把 236.9 GB 的权重流过一遍，token 的计算填不满它。B 变大以后，权重的开销被多个请求分摊，token 的计算显出来：B = 8 时 T 翻倍慢 55%。

**第三方评测算的「token/s」和另外两组不是一回事。** 它算的是回复里的 token：一条 512 个 token 的回复从头到尾（用整数模型生成回复、承诺分摊、证明）要 229–255 GPU 秒，所以是 2.027 token/s；正常 vLLM 服务是 2,669 token/s，相差 1,317 倍。它把这 1,317 倍拆成两部分：承诺加证明 118.2 倍，生成 1,199 倍。也就是说，它测到的时间里约 91% 是用整数模型生成回复，约 9%（每条回复约 21–23 GPU 秒）才是承诺和证明。仓库文档和我们算的是 prefill 的 token：每个请求 1,024 或 2,048 个输入 token 除以证明它的时间，不含生成。

**怎么读**

- **三组里由协议决定的量彼此一致**：proof 大小 18.7–18.8 MB、验证时间 18–21 秒、主机内存约 255 GB。我们 T = 2,048 的 24.5 MB 和 30 秒是这条线上新的一点。
- **由机器决定的量不同**：我们的 prefill 速率比仓库文档快 1.25–2.8 倍（B 越小差得越多），启动快一半。原因是显存带宽更高、没有降频、合成权重不读硬盘、CPU 更多，分不开各自的贡献。
- **第三方评测的 2.027 token/s 不能和 111 或 139 相比。** 把它拆开以后，承诺加证明的部分（每条回复约 21–23 GPU 秒）和我们的 23.8、仓库文档的 28.7 在同一量级。它的大头是用整数模型生成回复，这一步我们和仓库文档都没有计入。
- **第三方评测多测了一样东西：整条回复的覆盖。** 它的每个 proof 覆盖 512 个回复 token（exact match），而且 360 条全部通过。这和我们在 T = 1,024 下覆盖 1,000 个 token 通过是一致的；我们在 T = 2,048 下覆盖 1,000 个失败，是因为用的是 T = 1,024 的首选序列，不是程序的问题（见上文）。
- **T = 2,048 没有任何外部对照。** 三组里只有我们测了。

## 这些结果能说明什么

- 所有 `YES` 都来自改过的 C++ 验证器（`78092cbc`、`d1cc7d98`）。`d1cc7d98` 偏离了底层引擎 `blocks/iop/lkp.h` 写明的条件（键数严格少于 $2^{32}$），只用于这次实验，不用于服务。Lean 里证明过的验证器没有改，`guide/what-is-proved.md` 的结论不覆盖 lt 11。
- 权重是合成的（`-weights made-up-blocks`），形状是 Llama 4 Maverick 的。计算量由形状决定，所以时间可以参考；但没有运行过真权重。
- 每个数字来自一台机器、一次运行（`measure_rate` 的每个配置 3 批）。
- 这些位数（bits）不是安全等级（`guide/known-limits.md`）。运行结果不说明权重被隐藏了（`guide/weight-hiding.md`）。
- 覆盖 1,000 个 token 的请求在 T = 2,048 下失败的原因没有查清。
